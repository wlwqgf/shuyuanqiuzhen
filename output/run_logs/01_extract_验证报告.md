## 四、关键发现

本次运行验证了预期行为，同时暴露出三个必须在正式开发前解决的问题。这些发现比"脚本能跑"本身更有价值。

### 发现一：扫描件识别机制有效，但阈值需要按真实材料校准

脚本用"文字量 < 50 字"作为扫描件判据，成功识别出第 4 页（0 字）与第 5 页（22 字）。

**但该判据对真实年报过于粗糙**：真实年报中"图表页""目录页""签字盖章页"的文字量也常常低于 50 字，会被一并误判为扫描件。正式版 `src/ingest/extract.py` 必须改为多信号判定：

| 判据 | 含义 |
|---|---|
| 文字层字符数 | 基础判据 |
| 页面图像覆盖率 | 图片面积占页面比例 > 70% → 图文页 |
| 是否含表格结构 | 有线表格可直接抽 |
| 文字块坐标离散度 | 稀疏分布 → 图表页而非正文页 |

并将页面类型细分为：`text` / `table` / `chart` / `scanned` / `mixed`。

### 发现二：无边框表格无法被 `extract_tables()` 识别

`pdfplumber.extract_tables()` 在本样本第 2 页识别到 **0 个表格**，而该页确实是一张 9 行 3 列的会计数据表。

**根因**：pdfplumber 的默认表格检测依赖"线条"（单元格边框或行列分隔线）。本样本的表格没有边框，因此检测失败。**而真实年报中，无边框表格极为常见**——大量公司用留白与对齐代替表格线。

**验证**：PyMuPDF 的 `find_tables()`（基于版面分析）同样返回 0。

**后果**：若只依赖 `extract_text()`，表格的"行列对应关系"会丢失。在本样本中表现为数字被按阅读顺序拼成一行：

```
营业收入（元） 1,240,358,902.35 1,102,450,633.21
```

这行文字里，"1,240,358,902.35 属于 2024 年"这个信息**只存在于位置关系中**，纯文本无法表达。一旦材料里有跨年对比、多子公司并列表，纯文字抽取就会把不同主体、不同期间的数据混在一起，**直接制造出假错误**——这对"误报控制"是致命伤。

**解决方案（已确定技术路线）**：在 `src/ingest/` 中实现**基于坐标聚类的表格重建**：

1. 用 PyMuPDF `page.get_text("dict")` 取得每个文本片段（span）及其 `bbox` 坐标；
2. 按 `bbox.y` 聚类 → 得到"行"；
3. 行内按 `bbox.x` 排序 → 得到"列"；
4. 按行内片段数与横向间隔推断列边界 → 输出规整的二维表。

该方案不依赖表格线，对无边框表格同样有效。**这是 `src/ingest/` 的核心技术任务，必须在 10/14 前完成。**

### 发现三：列坐标越界会导致数字被"静默截断"

首次生成合成样本时，表格第 3 列坐标设置为 x=445，导致数值被截断：

| 应有值 | 实际抽取到 | 差异 |
|---|---|---|
| 1,102,450,633.**21** | 1,102,450,633.**2** | **丢失末位 1** |
| 3,541,706,231.**40** | 3,541,706,231.**4** | **丢失末位 0** |

**根因**：PDF 内置 CJK 字体中数字按全角宽度排布（宽度约等于字号），x=445 起排 17 个字符会越出页面右边界（595pt）而被裁掉。

**这个问题真正的危险在于它的隐蔽性**：截断后的数字 `1,102,450,633.2` 依然是一个格式完全正常的数字，看不出任何异常。如果核查系统拿它去和研报比对，会**凭空造出一个"数值错误"的误报**。

**对策（写入抽取层技术风险清单）**：

1. **数值完整性校验**：抽取到的金额若为小数，其小数位数应与该字段在原文中的形态一致；固定小数位字段（如千分位金额）出现位数异常即标记为 `suspected_truncated`，不得直接用于判定。
2. **边界检测**：文本片段的 `bbox.x1` 若接近或触及页面可用区右边界，标记为可疑。
3. **交叉校验**：关键指标（如总资产、营业收入）须与同页/同表其他数字建立勾稽关系互验（如分项之和 = 合计），不一致时拒绝判定。

## 五、结论

1. `01_extract.py`（v0 原型）**功能验证通过**：文字抽取、扫描件识别、页面渲染、体检报告四项能力均按预期工作，中文与数字无乱码。
2. 但原型**不足以支撑正式核查**，三个已识别的问题（扫描件判据过粗、无线表格丢失行列关系、越界截断静默发生）都指向同一个方向：**必须在抽取层做结构化重建与完整性校验，而不是把 PDF 当成一坨文字。**
3. 这三点已转化为 `src/ingest/` 的明确任务，优先级高于规则引擎与语义判定——**因为抽取错了一切都错，而且错得很隐蔽。**
