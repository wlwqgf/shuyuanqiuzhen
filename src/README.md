## 一、为什么这样切分：以"确定性"划界

本项目有两条不同性质的流水线，它们出错的方式完全不同：

- **确定性的计算**：一亿两千万除以八亿五千万等于多少、单位换算对不对、同比增速算得准不准。这类判断**可复现、可验证**，算错了就是错了，跑一百次结果一样。
- **不确定的语义判断**：这句话是什么意思、这个表述和报表是否矛盾、这条引用是否真实存在。这类判断**带概率性**，同一个输入不同模型可能给出不同结论。

因此代码按这两个性质分开：**确定性层归 B（`rules/`、`vision/`），不确定性层归 A（`agent/`、`ingest/`、`eval/`）**。两者的接口只有一个——数据契约（`common/schema.py`）。

接口越少，协作成本越低。两个开发人员各自独立推进，只在数据契约上对齐。

### 各模块职责详述

**`common/` —— 公共地基**

全项目共享的数据结构与基础设施。**依赖方向规则：本包被所有模块依赖，自身不依赖任何业务模块。** 反过来依赖会造成循环导入，必须避免。

- `schema.py`：定义 `FinancialFact`（从原始材料中抽取出的一条财务事实）与 `Finding`（一条核查结论），以及证据等级、错误类型等枚举。字段规范见 `docs/data_spec.md`。**该文件 10/13 12:00 后冻结，任何变更需 A、B 双签。**
- `trace_index.py`：页级溯源索引。解决"每条数据必须能追溯到原始来源页码"这一硬性要求——用 `doc_id + page_no + 字符区间` 三元组精确定位并回显原文。
- `logging_util.py`：统一日志出口。竞赛要求"完整记录文件访问、工具调用、计算过程和结果生成"，本模块负责把每一步写入 `trace.jsonl`。

**`ingest/` —— 材料解析入口**

把 PDF 变成机器可处理的结构。负责文字层抽取、表格抽取、页面渲染、页级索引生成、扫描件识别。**不做任何金融判断**——它只回答"这一页上有什么"，不回答"这页上的数字对不对"。

**`agent/` —— 编排与语义层**

系统的"大脑"。负责把原始材料组装成断言、调用大模型做语义判定、把规则层结论与语义层结论合并、生成改写建议、维护人工复核队列。

- `model_provider.py`：大模型调用的**唯一**入口。业务代码不得出现任何厂商接口地址。
  可用档案：`glm`（开发期默认，永久免费）、`deepseek`（决赛主力）、`qwen` / `kimi`（备选）、`ollama`（离线兜底）、`mock`（离线自检，**不得用于评测与展示**）。切换只改 `.env` 中的 `FINCHECK_LLM_PROFILE`，代码不动。选型依据见 `docs/tech_stack.md` §4。
- 待建：`orchestrator.py`（主流程编排）、`extractor.py`（LLM 断言抽取）、`verifier.py`（语义核验与证据分级）。

**`rules/` —— 确定性校验（owner: B）**

输入一条 `FinancialFact`，输出确定性的校验结论：勾稽关系是否成立、单位是否自洽、统计口径是否一致、估值倍数重算后是否相符。

要求：**每条规则独立可测**，规则文件用 YAML 存放在仓库根目录的 `rules/` 下（见第四节说明），代码负责加载与执行。

**`vision/` —— 图像处理（owner: B）**

三个落点：扫描件 OCR、图表数值还原、复杂表格结构还原。

**红线（不可违反）**：图像反推的数值带有误差，**不得作为自动判定依据**。凡由图像得出的证据一律标记为 C 级，只能输出"疑似"并进入人工复核队列。图像处理负责发现可疑，不负责定罪。

**`eval/` —— 独立评测框架（owner: A）**

读取标准答案（`bench/gold.json`，由 B 独立标注）与系统输出，计算准确率、召回率、F1、误报率、来源定位准确率，并支持在同一批材料上对比不同模型（消融实验）。

**隔离纪律**：本模块由 A 实现，标准答案由 B 标注，**两人互不查看对方细节**，直到评测跑完。目的是防止"规则写错了、标注也跟着错、评测还给满分"的自证循环。

## 四、容易混淆的两组同名目录

仓库根目录下也有 `rules/`、`bench/`、`output/`，它们与 `src/` 下的同名目录**职责完全不同**，不要混用：

| 路径 | 性质 | 内容 |
|---|---|---|
| `src/rules/` | **代码** | 加载与执行校验规则的 Python 代码 |
| `rules/`（根目录） | **数据** | 规则定义文件（YAML），每条规则独立成文件 |
| `src/eval/` | **代码** | 指标计算与实验对比的实现 |
| `bench/`（根目录） | **数据** | 评测集：`gold.json` 标准答案、`facts.md` 全队唯一可信数字源 |
| `output/`（根目录） | **产出** | 解析结果、图片、核查报告，可随时重新生成（图片与文本不入库） |

## 五、开发约定

**分支与合并**

| 成员 | 工作分支 | 可写目录 |
|---|---|---|
| A | `feat/agent` | `src/agent/`、`src/ingest/`、`src/eval/`、`src/common/` |
| B | `feat/rules` | `src/rules/`、`src/vision/`、`rules/`、`bench/gold.json` |
| C | `docs` | `docs/`、对外材料 |

A 为集成负责人，每日合并前必须跑通一次端到端。`src/common/` 归 A 维护，B 只读。

**代码约定**

1. **依赖方向单向**：`common` ← 业务模块。禁止业务模块间互相 import；跨模块协作通过数据契约（文件或数据结构）完成。
2. **路径不加硬编码绝对路径**：脚本内一律使用相对于项目根目录的路径。
3. **中文注释、英文标识符**：注释与用户可见输出用中文；变量名、函数名用英文。
4. **每个脚本可独立运行**：`python src/xxx/yyy.py` 必须能跑，并自带 `--help` 或自检模式，便于 B、C 自查。
5. **产出必带溯源信息**：任何经手模型的输出，必须记录所用厂商与型号（`ModelProvider.info()`）。
